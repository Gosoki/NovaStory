# 12 · 实测就绪性验证（2026-09-01）

> **这份文档回答一个问题：真把链接发出去、多个人同时在跑、网络不稳、有人手贱刷新，程序扛不扛得住。**
> 验证方式是**跑出来的，不是读代码读出来的** —— 全部固化在 `scripts/robustness_check.py`（`make robust`），

## 1. 本轮发现并修掉的 3 个真问题

### 🔴 ①「网关返回空串」全线静默 —— 被试点按钮毫无反应

**症状**：LLM **不抛异常、只是返回空内容**（拥挤网关的常见形态）时，六条生成路径全部静默失败：

| 路径 | 被试看到的 |
|---|---|
| C/D 首次生成 | 状态条写着「生成完成」，页面空白，下面一个「重试」按钮 —— 不知道发生了什么 |
| D「告诉 AI」 | **点了，什么都没发生** |
| E「完成作答,生成脚本」 | **点了，什么都没发生**；且首轮无草稿 → 连「取消」都没有 |

**为什么之前没发现**：`generate_json` 里**已经**专门处理了这种情况（注释写明「A congested free gateway can
return empty choices / null content」），说明作者遇到过 —— 但 **streaming 路径漏了同样的处理**。
所有调用方都写了 `if out and out.strip()` 守卫，守卫生效时静默 return，于是失败被吞掉。

**修法**（`views/_streaming.py`，单点，六个调用点全部受益）：流结束后文本为空即按失败处理 ——
记 `llm_error{kind:"empty"}` 事件 + 状态条标红 + 显示 `errors.llm_empty`（三语新增）。
调用方原有的失败分支（重试按钮 / 保留草稿 / 不落孤儿）随之全部生效。

**附带收益**：空返回率现在可事后统计（`llm_error.payload.kind == "empty"`），
这是**选网关/换模型的直接依据**，也是 Limitations 里该报的数字。

### 🟠 ② 题库写坏时，闸门不拦，被试撞崩且**已消耗一个拉丁方 seq**

`load_topics()` 对损坏文件是**静默回退种子主题**（不崩也不告警），而题数 < 3 时 `begin_rounds` 抛
`RuntimeError` —— 那一刻 `insert_participant` **已经执行完**：被试行已入库、seq 已被消耗，
留下一个永远走不完的孤儿，还把后续所有人的轮转挪了一位。

**两道修法**：
1. **部署前**：`deploy_check` 新增题库闸门 —— 文件损坏 / 顶层不是数组 / 题数不足 → 🔴；
   前 3 题三语不齐或镜数秒数越界 → 🟡。实测能拦住两种坏法。
2. **运行时**：`screening.py` 在 `insert_participant` **之前**校验题数，不够就报
   `errors.not_ready` 并返回 —— 兜住「采数期间有人改坏 topics.json」的窗口，**不消耗 seq**。

### 🟡 ③ 逐被试时长表落盘无视 `--csv`，污染项目树

`analysis/events.py` 新增的 `per_participant()` 原本硬编码写 `data/analysis/`，
被 `analysis_smoke` 的「自测污染了项目树」断言当场抓住。已改为跟随 `--csv` 同目录（两张表是同一批产物）。

## 2. 实测场景逐项结论

### A. 多用户并发（多人同时坐下开始）

| 场景 | 结论 |
|---|---|
| **24 人同一瞬间通过筛查** | ✅ 0.56s、零异常，seq = `0..17` + `0..5`，**无重复无跳号**。`BEGIN IMMEDIATE` 先取写锁再计数是对的 |
| 12 会话并发写 events（360 条） | ✅ 一条不丢 |
| **研究员后台读全表 × 被试并发写入** | ✅ WAL 下读写不互斥，读循环 116 轮零异常 —— **采数期间可以随时开后台看数据** |
| 同一轮重复提交 ×10（双击/多标签） | ✅ 只落 1 行，唯一索引 + `INSERT OR REPLACE` 生效 |

> 结论：**SQLite 单机足够扛这个规模**（N=36，实际并发个位数）。不需要换 Postgres。

### B. 断网 / 网关异常（11 项全绿）

| 失败形态 | 被试的出路 | 数据 |
|---|---|---|
| C/D 首次生成**抛异常** | 错误提示 + 重试按钮 | — |
| C/D 首次生成**返回空串** | 同上（**本轮修复**） | — |
| D 修改请求失败 | 错误提示，**草稿保留**，可继续改或直接提交 | ✅ 不留孤儿请求 |
| E 引导问题生成断网 | 错误提示 + 重试；**有草稿时另有「取消,返回草稿」** | — |
| E 引导 JSON 连续解析失败 | ✅ 降级为 1 道开放题，不卡死 | 降级事实落库（`fallback:true`） |
| E 终稿/修改稿生成失败 | 错误提示（**本轮修复**）；有草稿时可取消退回 | ✅ **不留孤儿引导轮** |

**「不留孤儿」为什么重要**：D 的修改请求和 E 的引导轮都是**只在生成成功后才提交**的。
若失败时先落库，历史面板的时间线（`requests[ai_idx-1]`）会错位，落库的 `revision_requests` /
`guidance_json` 也会多出一条没有对应 AI 版本的记录 —— 直接污染 E 的核心自变量。实测确认这条设计是对的。

### C. 中途刷新 / 多标签页

| 刷新时机 | 行为 | 评价 |
|---|---|---|
| 同意页 / 说明页 / 背景问卷 | 回到同意页，**不产生被试行** | ✅ 无脏数据，但**同意书说「会自动继续」在这里是假的** → 待拍板 ⑬ |
| 写创意阶段 | 续接回本轮开头 | ✅ |
| **已生成草稿后** | 本轮**从头重做**（草稿不保留） | ⚠️ 设计如此：trials 只在提交时才写。被试要重写创意重新生成 |
| trial 已交、问卷未答 | 重做该轮，`INSERT OR REPLACE` 覆盖 | ✅ 不产生重复行 |
| 反复刷新 | **不产生第二个被试行、不消耗第二个 seq** | ✅ 这是 `?t=` token 最重要的作用 |
| 同 token 双开两个标签页 | 两个 session 段 id 可区分 | ⚠️ 见 §4-① |
| **伪造/篡改 token** | 回到同意页，不崩也不泄露任何数据 | ✅ |
| 两名被试并行 | id / seq 均不同，session 完全隔离 | ✅ |

> 未走完 intake 的会话会留下 `participant_id` 永为 NULL 的事件行。**这不是脏数据，是 intake 流失率的唯一来源**
> —— 「多少人看了同意页就走了」此前无从得知。分析侧 `events.load_events` 的 `dropna` 已把它们挡在逐被试表之外。

### D. 脏数据 / 极端输入

- **超长 10 万字 / HTML 注入 / SQL 注入样 / emoji+零宽 / 纯换行 / 空串** → 全部**原样落库**，
  `parse_shots` 不抛，注入后表仍在（参数化查询）。
- **topics.json 非法 JSON / 空数组 / 顶层不是数组 / 脏字段** → 回退种子主题不崩
  （⚠️ 静默 → 已由新的部署闸门在部署前拦）。

### E. 后台配图线程

配图 API 全挂时 **2.5 秒内 settle**（每镜写 `.done` 标记），失败的镜降级为空画框。
**这条很关键**：`all_done()` 若不会 settle，问卷页的 2 秒轮询 fragment 会永远转下去。
实测确认「失败即静默降级、绝不打断实验」的设计成立。

## 3. 采数前的运维动作（`docs/paper/07` 的补充）

1. **开跑前一定跑三条链**：`make robust` + `make smoke-e2e` + `make smoke`，再 `deploy_check` 清红灯。
2. **每场前点一次研究员后台的「模型连通性探测」**（`admin.model_ping`）—— 它报通/不通 + 延迟，
   **>30s 会警告**。接口繁忙要在被试坐下前发现，不是在第一轮生成时发现。
3. **采数期间禁止改 `data/topics.json`** —— `_attempt_resume` 从文件实时重建 round_plan，
   改题会**静默重配**正在跑的被试（06 ⑨ #22 已记，零成本替代方案就是「别改」）。
4. **盯监控面板的三个数**：`llm_err`（现在含空返回）、`parse_fail`、`fallback`。
   任一显著非零就停下来查网关，不要让绿色的进度条掩盖坏掉的主 DV。
5. **备份**：`scripts/backup_db.sh` 进 cron（每日 + 每场后）+ 异地一份。
   WAL 模式下热备要连 `-wal`/`-shm` 一起拷，或用 `sqlite3 .backup`。

## 4. 已知残留风险（有对策 / 已判定可接受）

### ① 同 token 多标签页并发推进会互相覆盖
两个标签页各自推进同一被试，后提交的覆盖先提交的（`INSERT OR REPLACE`）。
**对策**：这是单人单坐的实验，现实概率极低；同意页已写「不要刷新/返回」。
**加固成本高**（要引入会话租约），**不做**。段 id 已能事后区分两段，真出了也认得出来。

### ② E 首轮生成持续失败时没有「跳过本轮」
第一轮没有草稿可退，只能反复重试 —— 与 C/D 首轮只能点「重试」是同一性质。
**对策**：接口彻底挂掉属于**实验员该介入的现场事故**（模型探测 + 监控面板会先亮），
而不是该给被试一个「跳过」按钮的场景（那会制造缺轮数据，直接违反「不完整数据弃用」的拍板①）。

### ③ `_run_with_progress` 的孤儿线程
引导 JSON 调用的忙等循环遇到 rerun（`StopException`）会跳过 `join()`，
留下一个**最长 120 秒**（`REQUEST_TIMEOUT`）的 daemon 线程。
**对策**：daemon 不阻止进程退出，N=36 全程累计也就个位数、每个活 ≤120s，**可接受**。
真要修见 06 ⑨（`try/finally` 兜底）。

### ④ DB 目录不可写（磁盘满 / 权限）
本轮**没能实测**（验证环境以 root 运行，绕过权限检查）。
代码路径上会抛 `sqlite3.OperationalError` → Streamlit 异常页 —— **是诚实失败，不是静默丢数据**。
**对策**：部署时监控磁盘水位；`backup_db.sh` 进 cron 时顺便加一条剩余空间告警。
数据库本身很小（N=36 全程 < 50 MB，含配图），正常情况撑不满。

## 5. 这次没测、也不打算测的

- **真实网络抖动 / TLS 中断**：需要真部署 + 流量注入才有意义，桩测不出新东西。
  应对手段（120s 超时 + 首 token 前自动重试 ×2 + 手动重试按钮）已在 B 段验证过等价路径。
- **浏览器兼容性**：Streamlit 自己保证；被试用什么浏览器不受我们控制。
  唯一自写的前端是问卷页的分镜表钉住脚本（`questionnaire.py` 的 `_SB_SCROLL_JS`），
  它有 `sb-js` 渐进增强开关 —— **脚本没跑起来时退化成普通在流内的表格，被试照样看得见分镜**。
- **负载压测**：目标 N=36、实际并发个位数，A 段的 24 路并发已远超真实峰值。
