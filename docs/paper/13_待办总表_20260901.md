### ⚠️ 2.2 的实测结果 —— 这是本轮最重要的数字

```
子集 N     MDES(80%)   要达到它，全样本得招多少人（占比 60% / 50% / 40%，含 20% 流失）
15          dz 0.77      33 / 38 / 48
18          dz 0.71      39 / 45 / 57
22          dz 0.63      47 / 55 / 69
27          dz 0.56      58 / 68 / 85
36          dz 0.46      77 / 90 / 113
```

**`11` rank3 预警的「N≈18 时 MDES≈dz 0.70」得到实测确认（0.706）。**
对外宣称的 dz≈0.48 是**全样本**数字；主分析跑 novice 子集，要达到同等灵敏度需招 **77–113 人**。
→ **子集目标 N 是冻结的最后一块拼图**，而它取决于招募渠道与时间账（第 3 层）。

### 2.4 我为什么选「降为描述性」而不是「换个有方差的代理」

H4 的 DV 是 `spec_ok = int(n==3 and dur_ok)`，**二值**，而 `02 §8.2` 实测三条件的镜数与时长合规都是 **100%**。
换成 MATTR/HD-D 或「终稿↔首版距离」确实有方差，但它们量的是**词汇多样性/改动量**，不是质量——
把它们改名叫质量 DV 是偷换概念，比诚实地说「没测」更糟，而且会正面撞上 `01` 的禁用措辞表。
所以：`structural_completeness` 继续算继续报，但只作描述性（**三条件都能产出合规分镜**这件事本身就是结论）；
论文与幻灯片必须写「本研究は作品の質（美的・物語的）を測定していない」。

## ⑦-D 设计语言统一 + 手机适配（2026-09-02 凌晨）

**方法**：不再靠读 CSS 猜。用 Playwright + chromium 起一个**隔离实例**（临时库 + 打桩 LLM，

### 实测到的三个手机端问题（都不是猜的）

1. **7 点量表的锚点在窄屏堆成阶梯** —— `_scale._render_anchors` 用 `st.columns(3)` 拼，
   而 Streamlit 在窄屏会把列**竖着堆**。于是「まったくそう思わない／どちらともいえない／
   非常にそう思う」变成三行，各自左中右对齐，读起来是一道斜梯 —— 而且
   **看不出哪一句属于哪一端**。对一个靠锚点定义刻度含义的 7 点量表，这不是难看，
   是量表在手机上失去了刻度说明；全study 13 个量表题**每一题**都中招。
   → 改成一行 flex（`.ns-anchor`），窄屏也不拆行；每题从约 6 行缩到 3 行。
2. **分镜表在窄屏被压成竖排单字** —— 5 列的固定百分比（7/14/33/28/18%）是给 ~900px 桌面
   调的，到 390px 就成了 27/55/129/109/70 px。实测截图：表头「No.」竖排成 N/o/.，
   「クローズアップ」在 55px 里折四行并压住镜号圆圈，「セリフ・音」整列变成一列单字带子
   （静／か／な／寝／室）。**而问卷页正要求被试对照这张表回答所有权与保真** —— 读不了表，
   答的就不是同一道题。
   → `@media (max-width:700px)` 下表格改成**每镜一张卡**：镜号+景别一行、画框整宽、
   内容与台词各带回自己的列名（`td[data-col]` + `::before`），装饰用的空白行收起。
3. **展开侧栏的 » 箭头浮在正文上** —— 是 §① 把顶栏改透明的副作用：手机上正文滚到顶部时，
   箭头压在题干中间，读起来像正文混进了一个乱码字符（三屏截图都出现）。
   → 给它一个圆形半透明底 + 模糊，明确是悬浮控件而不是一个字。

另修：窄屏字阶（实测 `h1` 在 390px 上是 **44px**，一个分节标题能吃掉三行屏幕）。

### 设计语言：单一真源

颜色字面量原本有 **24 个互不相干的值**，散在 `app.py` / `intro.py` / `round_common.py` /
`_scale.py` / `_storyboard.py` —— 同一种「弱化的小字」在三处是三个灰度。
现在全部收进 `app.py` 顶部的一个令牌块（`:root` + `prefers-color-scheme` 两档）：

| 令牌 | 语义 |
|---|---|
| `--ns-go` / `--ns-go-hover` | 绿 = 决定 / 推进 / 定稿（所有 `type="primary"`） |
| `--ns-ai` / `--ns-ai-hover` | 蓝 = 继续和 AI 折腾（`btn_more_ai`，明确的非终局动作） |
| `--ns-accent` | 蓝 = 强调「读这句」（说明页的两句引导语） |
| `--ns-dim` | 弱化 = 注解 / 锚点 / 提示（所有 caption 级文字） |
| `--ns-line` / `--ns-soft` / `--ns-radius` / `--ns-fs-note` | 细线 / 弱填充 / 圆角 / 注解字号 |
| `--ns-chrome` | 浮在正文上的控件底 |

绿蓝两档必须泾渭分明：Streamlit 默认的 primary 是珊瑚红，新手会读成「危险操作」。
`_storyboard.py` 的絵コンテ纸色（`#fbfaf3` / `#3f3f3f` / `#9a958c`）是**刻意的子主题**，
保留不动，但已在注释里写明它是子主题而不是漏网之鱼。

**验证**：两个视口各 12 屏，**0 屏横向溢出**；桌面端渲染与改动前逐屏比对无回归；
五条验证链（i18n 294 键 / E2E / robust 34 项 / 4 场实跑 40 断言 / analysis 25 断言）全绿。

### 2.3 两个主终点都没有各自的 SESOI，四象限里的「≈（不劣）」统计上是空的 【已核实】

### 3.5 研究员现场 SOP 不存在

- **问题**：`12 §3` 只覆盖机器侧（跑三条链、模型探测、别改题库、盯三个数、备份）。面向真人的那一半没有：被试坐下前说什么、被试问「哪一轮的 AI 更好」怎么答（**必须统一回避，否则临场解释成为未记录的处理变量**）、什么时候点 reset、每场后要做哪几件事。
- **方法**：写一页可打印的 checklist：每场前 3 步 → 开场标准话术（ja 逐字稿，只讲流程不讲假设）→ 常见提问的标准答法表 → 每场后 3 步（记录场次日志 → 跑备份 → reset）→ 当日收尾（核对 seq 平衡、导出监控三个数）。
- **影响**：没有统一话术，实验员的临场解释直接威胁被试内比较；「每场后备份」`07` 已明写为要求，没有 checklist 必然漏做。

### 3.6 离脱处置与 seq 补发机制不存在

- **问题**：`12 §1②` 已确认「被试行入库后走不完 = 那个 seq 被永久消耗」，`11` rank3 指出 `seq = n % 18` **无法定向补空格**。但没有任何文档写：多久没动作算离脱、要不要人工补这个 seq、离场者能否重来、OpenAI 大面积故障时该场如何标记。
- **方法**：①定义离脱判定（建议 24 小时无事件 → `status='abandoned'`）；②给后台加「指定下一位被试的 seq」入口（十几行），**或**事先声明「不定向补，靠超招募随机填」并接受各 seq 完成数不均；③写明故障时的场次标记与是否重招同一人（重招则条件暴露顺序作废）。

## ⑦-M 首屏加载加速（2026-09-03）

**起因**：从中国打开页面偏慢。先量后改，没有猜。

**根因**：Streamlit 1.60 的 `SelectiveGZipMiddleware` **主动让 `/static/` 绕过 gzip**，源码注释写的理由是「本地压测显示 bypass 能改善首屏与峰值 RSS」。那个结论在局域网成立（压缩的 CPU 开销大于省下的传输时间），在跨境高延迟链路上正好反过来。实测首屏 122 个请求、2.50 MB，`Content-Encoding` 全为空。页面里**没有任何外部域名**（字体是本地的），所以跟被墙无关。

**已改（代码，不涉及实验设计）**：

| 文件 | 作用 |
|---|---|
| `scripts/precompress_static.py`（新） | 离线 gzip -9 静态资源；`--check` / `--clean`；产物在 `.venv` 内，不进 git |
| `scripts/serve.py`（新） | 生产启动入口。建 app 前替换 `StaticFiles.file_response`，命中时直接发预压缩产物；运行期零压缩开销 |
| `Makefile` | 新增 `precompress` / `serve` |
| `deploy/novastory.service` | `ExecStart` 改走 `serve.py`，加 `ExecStartPre` 自动预压缩，`ReadWritePaths` 放开 `.venv` |
| `deploy/Caddyfile`（新） | HTTPS + HTTP/2 反代模板，含安装命令 |
| `scripts/deploy_check.py` | 新增「静态压缩」闸门：产物是否最新 **且** 服务是否真由 `serve.py` 启动 |
| `DEPLOY.md` | 新增 §4.5，§5 补 HTTP/2 收益 |

**效果**（模拟 200 ms 往返 / 4 Mbps）：线上字节 2.50 MB → **0.77 MB（−69%）**，首屏 8.6 s → **6.4 s（−26%）**。231 个文件压到 30%。20 项定向断言通过，重点覆盖「什么时候不能发 .gz」：不支持 gzip、Range 请求、非 200、白名单外后缀、**产物比源文件旧**（升级 Streamlit 后的唯一防线，过期即回退发原文）。

**待拍板 ①：切换线上服务的启动入口。** 改 `/etc/systemd/` 被本机安全策略拦下，需你自己执行。当前服务仍是旧入口，**优化尚未在线上生效**，`deploy_check` 的「静态压缩」为 🔴。命令见本轮报告。这一步也可以并进「transient → 持久单元」那条红灯一起做。

**当日追加发现（把上面两条待拍板的前提改了）：线上早已有 nginx 反代 + 有效证书 + HTTP/2**，对外地址 `https://test.jp.wuzuxi.com`，后端 etag 与本机 8501 一致。nginx 不在本机，所以 `deploy_check` 原来那条「没有任何进程监听 :443 → 无 HTTPS 反代」是**误报**，已改为读 `secrets.toml` 的 `public_url` 从外面实测（新增 `check_public`，`check_runtime` 不再自行判 443）。

由此 HTTP/1.1 六并发那 4 秒本来就不存在，**真正缺的只有反代层的 gzip**。实测（200 ms / 4 Mbps）：

| 状态 | 协议 | 线上字节 | 首屏 |
|---|---|---|---|
| 线上现状 | h2 | 1.96 MB | 5.8 s |
| 开压缩后 | h2 | 0.61 MB | **2.4 s** |

**待拍板 ②：已完成（2026-09-03 当日）。** 反代（OpenWrt 上的 nginx）已开 gzip，线上实测确认 `content-encoding: gzip`。首屏从 5.8 s 降到 **2.4 s**，线上字节 1.96 MB → 0.68 MB。`deploy_check` 的「对外地址」项转 🟢。

由此「静态压缩」那条的严重性也随之下调：压缩既可由 app（`serve.py` 预压缩）承担，也可由反代承担，被试收到压缩字节即达标。闸门改为读 `check_public` 的结论判严重性——反代已压时降为 🟡（提示切 `serve.py` 可再省反代的 CPU，且用上 level 9），只有两边都没压才是 🔴。

顺带实测了 gzip 级别的取舍（首屏 104 个 JS / 2.10 MB，2012 年低功耗 Xeon）：level 1 压到 30% 耗 26 ms，level 5 压到 26% 耗 49 ms，level 9 压到 25% 耗 89 ms。**收益递减极快，反代跑在路由器上时用 level 1~2 即可**；配合一年 `immutable` 缓存，每位被试只压一次。

**待拍板 ③：app 仍绑 `0.0.0.0:8501`。** 反代之外留着明文直连入口，可绕过 HTTPS 摸到应用。改 `--server.address 127.0.0.1` 即可，与待拍板 ① 的 systemd 改动是同一次操作。

**JS 合并被否决（不必再考虑）。** 三路调研实测：363 个 JS 里首屏只加载 104 个（2.10 MB 原文 / 0.51 MB 压缩），其余 259 个是 React.lazy 按需分包，Plotly 4.7 MB、DeckGL 2.4 MB、代码高亮 1.5 MB 本项目一次都没用到。合并会把它们全部拉进首屏，且 142 处动态 import、152 处 `import.meta.url`、6 处 Web Worker 会直接失效（气球/雪花等 `../media/` 资源 404）。删 `modulepreload` 提示也省不掉任何请求：那 103 个提示恰好等于入口的静态 import 闭包（差集两侧均为 0），删掉只会让并行预取退化成三层串行往返。**Streamlit 官方的代码分割已经做到位，没有剩余空间。**

**不做 CDN 的理由**（你提到「加速源」）：① 正式被试是日本人，中国访问慢主要影响你自测；② Streamlit 的 `index.html` 用相对路径引 103 个 `modulepreload`，改指 CDN 要改写它，升级 Streamlit 即失效；③ 真要提速，把服务器放到离被试近的地方比套 CDN 更直接。若最终仍想用 CDN，这属于部署决策，需要你定。

**排查**：先怀疑 Streamlit 的 stale 半透明与分镜表 `opacity:0 → 1` 淡入，都用真实浏览器量过——**问卷区与分镜表的 opacity 全程都是 1.00**，两张截图逐像素完全相同，两个假设都不成立。把复现逐步逼近真实场景（真实 `_storyboard.render` + `pin=True` + 配图按 4 秒逐张到达 + 模拟 200 ms/4 Mbps 链路）后才复现出来，并用逐帧像素差定位到：

**根因**：`questionnaire.py` 的 `_SB_SCROLL_JS` 里 `measure()` 每个 tick 都执行 `slot.style.height = natH + 'px'`，而 `natH = sheet.offsetHeight` 是**取整**的。配图逐张到达时表格实际高度有亚像素变化，取整后在相邻两个整数间来回跳，于是占位 slot 的高度被反复改写，下方整块问卷跟着上下抖 1 px。差异图上「本轮问卷」标题呈现明显重影。

**修复**：`measure()` 加 1 px 死区，`Math.abs(natH - curH) > 1` 才改写 slot 高度。新 slot 的 `style.height` 是空串（`parseFloat` 得 NaN 归 0，差值必然 > 1），所以「新节点拿回占位高度」仍成立；真实高度变化（图片让表格长高几十像素、下一轮脚本更长）远超死区，照样生效。

**验证**：同一构图下差异区 bbox 从 `(79, 62, 656, 898)` 收缩到 `(442, 62, 656, 273)`，不再延伸进问卷区；标题重影消失。滚到问卷区后 pin 行为不变（新图只更新右上角缩略图，问卷零位移）。验证链九项 + 76 + 23 项断言全绿。

**顺带记录**：`imagegen.frame_htmls` 每次轮询都把**已生成的全部图片**重新 base64 内联，三张图约 76 KB，生成过程中至少传 146 KB（实际只需 76 KB）。在 4 Mbps 链路上一帧约 0.16 秒，目前不构成问题；若将来镜数增加或改用更大的图，应改走 Streamlit 的 media URL 让浏览器缓存。已加一层按 (路径, mtime_ns, 大小) 的 base64 缓存（0.7 ms → 0.15 ms），但**这点开销本来就不是瓶颈，别把它当成本条的修复**。

### 真正的「暗下来」：被试每点一次选项，整页变成 opacity .33

上面的抖动修完后，并行调研查清了另一条独立机制——这才是被试反馈的主因，也解释了我最初四轮复现为何都失败：**我从没点过问卷选项**。

- Streamlit 给每个 `.stElementContainer` 打 `data-stale="true"` 并施加 `opacity:.33` + `transition:opacity 1s ease-in .5s`（值在已构建产物 `utils.94RcZhG4.js` 的 `{secondary:.6, stale:.33}`）。
- fragment 因 `run_every` 自动重跑时，判定函数只把该 fragment 内的节点标 stale（实测 **1/13** 个元素）。
- **但被试点一次量表选项是一次全量 rerun**（widget 消息不带 fragmentId），`fragment_ids_this_run` 为空 → 整页标 stale（实测 **12/13**）。
- 那 0.5 秒延迟意味着只有 rerun 超过 0.5 秒才看得见。配图生成期间问卷页要重建整张分镜表，轻易超过——于是「答一题、整页暗一下」。

**A/B 实测**（人为把 rerun 拖到 2.5 秒，让淡入跑满）：

| | 峰值 stale 元素 | 问卷区 opacity 轨迹 |
|---|---|---|
| 无 CSS 覆盖 | 13 | 1.00 → 0.93 → 0.80 → 0.64 → 0.45 → **0.33** |
| 有 CSS 覆盖 | 13 | 全程 **1.00** |

**修复**：`app.py` 的 `_DESIGN_CSS` 加一条
`.stElementContainer[data-stale="true"]{opacity:1!important;transition:none!important}`（另覆盖 expander/tabs 头）。特异度 (0,2,0) 高于 emotion 类的 (0,1,0)。Streamlit 1.60 **没有**任何官方开关能关掉这个效果（config 里无 `runningIndicator` 之类，theme 的可配项里没有 opacity）；`data-stale` 是已构建产物里唯一稳定的钩子，升级后若失效，表现只是「变暗回来了」，不会白屏。

**⚠️ 这条改变了被试所见的界面，需要你追认。** 我判断利大于弊并已上线，理由：本轮问卷里就有 NASA-TLX 的负荷题与挫折感题，**界面反复闪烁本身会推高这两项评分，而闪烁频率与条件相关**（E 的分镜生成更晚、rerun 更慢），属于系统性污染；而加载反馈并没有丢——分镜画框在图片没好时一直显示「生成中」文字占位，进度信息由那句话给足了。若你认为应保留原生加载反馈，撤掉那三行 CSS 即可。

## ⑦-P 实证：生成期间推进按钮未禁用，重复点击会不断重启生成（2026-09-04）

在反代地址上真实跑流程时撞到的。自动化脚本每 5 秒点一次「确定，开始创作」，结果 participant id=5 的第 2 轮（E 条件）留下 **`llm_start` 87 次、`llm_done` 仅 1 次**，且**没有任何 error / fail / abandon 事件**——每次点击都 rerun，rerun 打断上一次流式调用并重新发起，于是永远走不完。

这坐实了审计里那条未送验的 medium（`views/_first_gen.py`：「断线会杀掉生成，pipeline 阶段无上限自动重生成且 `n_llm_calls` 虚高」），并补上了两点它没说的：

1. **推进按钮在生成期间仍然可点**，没有 `disabled`，也没有任何"正在生成、请勿重复点击"的拦截。
2. 重启不留痕：只多一条 `llm_start`，被打断的那次**连 `llm_abandoned` 都没记**（该埋点只覆盖部分路径），所以事后从 `n_llm_calls` 看只会以为被试点了很多次，看不出是同一次任务被反复重启。

**真实被试会不会这样？** E 条件的引导生成较慢，被试等不及多点两下是现实的。后果是白烧 token、`n_llm_calls` 虚高（它进事件层指标），极端情况下走不完。

**待拍板（未改）**：最小修法是在 `r_phase == "pipeline"` 期间把推进按钮 `disabled=True`，或在点击时判重（同一 attempt 已有未完成的 llm_start 就忽略）。这属于被试端交互变更，且要小心别把「生成真的失败后需要重试」的路径一起堵死，所以先记录不动。

## ⑦-Q 拉丁方序号可释放 + 监控面板加会话列表（2026-09-05）

**起因**：问「序号什么时候回收」。答案是**从不回收**——`insert_participant` 每次现数一遍 `seq = (passed=1 且非 dev 的行数) % 18`，计数条件里没有 `status`，所以**通过筛查那一刻就占住一个格子**，之后关页面再也不回来，格子照占。当时库里 13 人占了序号 0–12，实际走完的只有 3 人。

18 个 Williams 序列要平衡就得每格人数相等，被弃号占着的格子会一直缺人。而 `_TARGET_N = 36` 正是 18 的两倍（每格 2 人）；若只有 30 人完成，序号 0–11 各 2 人、12–17 各 1 人，本身就不平衡，再叠加中途流失会更歪。**招募量应按「完成 36 人」倒推，多招几个补流失。**

### 设计变更：序号分配由「计数」改为「补最少用的格子」

```python
# 旧： seq = count % 18
# 新： seq = min(range(18), key=lambda k: (已用次数[k], k))
```

两者**在没有空缺时逐个等价**（实测连续 20 人：`0,1,…,17,0,1` 完全一致）。区别只在有人被释放之后：

| | 释放 seq=5 后，下一个人拿到 |
|---|---|
| 旧（计数） | `12 % 18 = 12` —— 12 已被占用 → **重复**，而 5 的空缺永不填补 |
| 新（补缺） | **5** —— 正好补上，分布保持各格相差 ≤1 |

实测已验证四点：等价性、补缺、旧逻辑的重复（对照）、释放后分布仍平衡。

### 新增 `db.release_participant(pid)`

把 `screening_json.dev` 置 1 并记 `released_at`，**不删行**。删行会让后续序号算错、也毁掉已采到的部分数据；标记 dev 则让这一行同时从三处退出——序号分配、`v3.included_participants`、监控面板统计——与 devtools 注入的测试行走同一条排除路径，口径一致。

⚠️ **被释放者的 token 仍然有效**：他拿着 `?t=` 回来还能走完，只是数据不进分析。所以只对确认不会回来的会话用。

### 监控面板新增「进行中的会话」

`views/monitor_panel.py` 的 `_sessions()`：列出所有 `in_progress` 行，含**编号 / 序号 / 开始时间 / 最后活动 / 已交轮数 / 释放**。最后活动取该被试 `events` 的最大 `ts`，用来判断人是否真的走了。顶部显示当前保持连接的 WebSocket 会话数（`Runtime._session_mgr.list_active_sessions()`，内部 API，取不到就静默跳过，不影响功能）。释放按钮包在 `st.popover` 里，需二次确认。

i18n 三语各新增 13 个 `monitor.*` 键（327 键 × 3 一致）。验证链九项 + 76 + 23 项断言全绿。
